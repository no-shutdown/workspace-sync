# 架构地图与单根开发任务树设计

- 状态：accepted
- 日期：2026-07-27
- 基于：ADR-0083 的四类正式节点和支撑记录设计

## 背景

当前分层视图已经把系统、能力、缺口和任务分开，但架构关系和任务关系仍容易在同一张图中相互干扰。用户需要同时回答两个不同问题：系统架构如何组成，以及当前开发工作如何拆解和推进。前者适合有方向的关系图，后者适合单根、有层级的任务树。

## 决策

### 1. 保留两种独立结构

- 架构结构由系统之间的 `包含`、系统提供的能力和系统存在的缺口表达，投影到 `架构地图.md`。
- 开发结构由任务之间的 `分解为` 表达，投影到 `开发任务.md`。
- 任务的 `依赖` 是跨树枝的执行前置关系，不改变任务父子层级。
- `解决`、`涉及系统`、`目标能力` 和 `需要联调` 是任务与架构的交叉引用，不参与任务树排序。

两个视图可以互相跳转，但不把另一种结构的边画成自己的主结构边。

### 2. 开发总任务是唯一根节点

每个 workspace 的正式任务树有且只有一个根任务：

```text
图谱/节点/任务/任务-开发总任务.md
```

根任务仍然是正式类型 `任务`，frontmatter 额外使用 `task_role: 根任务` 标识。根任务不是新的节点类型，也不替代 `工作区.md`。只有用户确认了 workspace 的总体开发目标后，compile 才能创建或更新这个根任务。

任务树约束：

- 根任务没有 `分解为` 父级；每个其他正式任务必须且只能有一个 `分解为` 父级。
- `分解为` 只能连接任务到任务，必须无环；不能用系统、能力、缺口、项目或决策作为任务父级。
- `依赖` 可以跨越不同任务分支，但不产生额外根节点，也不改变父级。
- 没有明确父级、存在多个父级、无法从根到达或出现循环时，只报告 warning；不按名称、项目或最近编辑内容自动挂接。
- 缺少确认父级的工作保留为候选或未定位任务，不伪装成正式树节点。

根任务页面和任务视图显示子任务数量、完成/进行中/阻塞统计；这些是派生摘要，不静默改写正式任务状态。

### 3. 视图职责

主视图调整为：

| 页面 | 结构 | 内容边界 |
| --- | --- | --- |
| `架构地图.md` | 图 | 系统层级、能力、缺口摘要；不画任务树或项目/决策节点 |
| `开发任务.md` | 树 | 从 `任务-开发总任务` 递归展开任务、状态、依赖、涉及系统、解决缺口和下一步 |
| `开发路线.md` | 桥接索引 | 以系统/缺口为入口列出解决任务，不生成第二套任务层级或大型 Mermaid 图 |
| `系统联调.md` | 关系图 | 系统之间的 `需要联调` 关系及相关任务引用 |

`任务清单.md` 不再作为正式页面名称；当前页面迁移或重命名为 `开发任务.md`。`总览.md` 同时链接架构地图和开发任务树，并显示两条面包屑：任务树位置和架构位置。

### 4. 任务树的阅读格式

`开发任务.md` 默认使用根优先的 Markdown 嵌套列表或标题层级，避免把依赖线绘制成树边：

```text
开发总任务
├── 搭建系统基础能力 [进行中]
│   ├── 完成数据模型 [已完成]
│   └── 完成认证机制 [待开始]
├── 实现核心业务能力 [进行中]
│   └── 增加幂等校验 [进行中]
└── 完成系统联调 [待开始]
```

每个任务项旁边显示架构位置摘要，例如“业务平台 / 数据导入缺口”，以及依赖和实现项目支撑记录的链接。实现项目只作为支撑信息，不成为任务树节点。

### 5. 架构地图的阅读格式

`架构地图.md` 使用 Mermaid 或列表投影展示：

- `包含` 形成系统层级主干；
- `提供` 连接系统与能力；
- `存在缺口` 以缺口数量或局部缺口节点表达；
- 任务只通过局部链接或摘要被引用，不成为架构图主结构；
- 项目、决策、候选和健康问题不进入主图。

## 编译与健康检查

compile 生成根任务链接、任务树和桥接索引。它必须检查：

1. 根任务数量是否为一；
2. 每个非根任务是否恰好有一个 `分解为` 父级；
3. `分解为` 是否只连接任务、是否存在循环；
4. 所有正式任务是否都能从根任务到达；
5. `依赖` 是否被错误地当作父子关系；
6. 任务是否能通过 `解决` → `缺口` → `存在缺口` → `系统` 或 `涉及系统` 定位到架构。

这些问题是 warning，不自动创建父级、合并任务或改变任务状态。根目标未确认时可以生成待确认候选，但不能生成正式根任务。

## 迁移兼容

- `图谱/视图/任务清单.md` 迁移为 `图谱/视图/开发任务.md`。
- 旧的 `图谱/视图/开发任务.md` 若存在，先作为旧生成页面备份/预览处理，再由新编译器重建，不把旧列表内容当成新的任务事实。
- 现有正式任务保留稳定 ID、aliases、来源、正文、状态和历史；缺少父级的任务进入未定位 warning，不自动挂到根任务。
- 旧的 `分解为` 和 `依赖` 关系继续保留，迁移只修正端点和页面链接，不把依赖转换为父子关系。

## 结果与取舍

正面结果：

- 架构图可以保持稳定、稀疏，专注回答系统位于哪里；
- 任务树有单一入口，能直接回答开发总任务当前推进到哪一层；
- 缺口和任务仍通过桥接索引互相追溯；
- 不引入新的正式节点类型或 Obsidian 插件依赖。

代价：

- 任务需要补齐父级，历史任务可能出现未定位 warning；
- `开发路线.md` 不再是第二棵任务树，只承担缺口到任务的交叉导航；
- 根任务和子任务状态摘要必须与正式状态区分，避免把统计推断当作事实。

## 验收标准

- 规范只保留四类正式类型：系统、能力、缺口、任务；
- 每个 workspace 的任务树明确链接到唯一 `任务-开发总任务.md`；
- `架构地图.md` 不包含任务树结构边，`开发任务.md` 不包含系统层级结构边；
- `开发任务.md` 是根优先的树，依赖以列表/标记展示；
- `开发路线.md` 是桥接索引，不生成第二套层级；
- 总览同时给出任务面包屑和架构面包屑；
- 旧 `任务清单.md` 和任务树异常都有明确迁移/健康检查规则；
- active skill 与源 skill 文档一致。
