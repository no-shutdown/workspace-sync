# 开发图谱核心类型精简设计

## 背景

当前 `workspace-sync` 将项目、系统、能力、能力缺口、任务和决策都作为正式图谱类型处理。这个模型能够表达较多语义，但把架构对象、当前问题、执行动作和支撑资料放在同一层，导致 Obsidian 全局图谱和类型目录的认知成本偏高。

本设计针对个人开发知识库的主要目标：

1. 一眼看出当前开发位于整体系统架构的哪一层、哪一个能力链路。
2. 一眼看出当前能力缺口和对应开发任务。
3. 让项目仓库和技术决策仍可追溯，但不污染主架构图和任务图。

## 目标与非目标

### 目标

- 将正式图谱类型从六类收敛为四类：系统、能力、缺口、任务。
- 保留能力和缺口的语义区别，避免把目标能力与当前问题混为一谈。
- 将项目和决策降级为支撑记录，不作为主图谱节点类型。
- 用系统层级、缺口链路和任务状态生成互相聚焦的视图。
- 为每个活动任务提供稳定的架构定位。
- 迁移旧节点时保留稳定 ID、来源、正文和历史。

### 非目标

- 不把知识库改造成代码项目管理系统。
- 不删除已有节点或自动合并疑似重复节点。
- 不把所有节点重新塞进一张全量 Mermaid 图。
- 不根据“没有能力链接”自动推断能力缺失。
- 不改变 workspace 隔离、Obsidian CLI、Git 同步和任务状态确认规则。

## 核心模型

### 正式节点类型

正式节点只保留四类：

| 类型 | 语义 | 主要问题 |
| --- | --- | --- |
| 系统 | 具有运行或架构边界的单元 | 架构由哪些系统组成 |
| 能力 | 系统应该提供或已经提供的可观察行为/结果 | 系统需要具备什么能力 |
| 缺口 | 当前能力与目标之间已确认的缺失 | 现在具体差什么 |
| 任务 | 可执行、可跟踪的开发工作 | 下一步要做什么 |

节点路径和文件名统一为：

```text
图谱/节点/<类型>/<类型>-<中文名称>.md
```

例如：

```text
图谱/节点/系统/系统-业务平台.md
图谱/节点/能力/能力-数据导入.md
图谱/节点/缺口/缺口-数据导入缺少幂等校验.md
图谱/节点/任务/任务-实现数据导入幂等校验.md
```

稳定 `id` 仍保存在 frontmatter 中。类型或名称变更不会改变稳定身份；旧类型和旧文件名写入 `aliases`，用于迁移期间的历史链接解析。

### 支撑记录

项目和决策继续保存，但不属于正式图谱类型：

```text
图谱/说明/项目/<项目名称>.md
图谱/说明/决策/<决策名称>.md
```

项目记录负责保存规范化 remote、分支、HEAD、upstream 和 dirty 状态；本机路径仍只保存在本地 state。任务或系统可以记录实现项目，但该信息不参与架构层级和主 Mermaid 图。

决策记录保存已确认的技术选择、理由和影响。需要追溯时可以从正式节点引用决策说明，但决策不会进入架构地图、开发路线和任务清单的主图。

联调不创建节点。系统之间使用 `需要联调` 关系；只有需要保存详细接口、数据、时序或验证规则时，才在 `图谱/说明/联调/` 下保留普通说明页。

## 关系模型

正式图谱关系如下：

| 关系 | 起点 → 终点 | 用途 |
| --- | --- | --- |
| 包含 | 系统 → 系统 | 表达架构父子层级 |
| 提供 | 系统 → 能力 | 表达系统明确提供的能力 |
| 存在缺口 | 系统 → 缺口 | 表达系统当前缺少的具体能力 |
| 目标能力 | 缺口 → 能力 | 指向缺口对应的目标能力 |
| 解决 | 任务 → 缺口 | 表达任务要解决的缺口 |
| 涉及系统 | 任务 → 系统 | 给没有缺口链路的任务提供架构定位，也表达跨系统任务 |
| 分解为 | 任务 → 任务 | 表达任务层级 |
| 依赖 | 任务 → 任务 | 表达执行前置关系 |
| 需要联调 | 系统 → 系统 | 表达系统之间需要共同验证 |

任务状态仍固定为：`待开始`、`进行中`、`已阻塞`、`已完成`、`已取消`。任务的项目关联和决策引用属于支撑信息，不作为正式图谱关系参与主视图。

关系正文示例：

```md
## 关系

- 涉及系统：[[系统-业务平台]]
- 解决：[[缺口-数据导入缺少幂等校验]]
- 依赖：[[任务-完成认证改造]]
```

系统层级只使用 `包含`；任务层级只使用 `分解为`；任务前置条件只使用 `依赖`。三者不能互换。

以下辅助关系继续保留，用于历史和溯源，但不参与架构路径计算，也不进入架构地图、开发路线和任务清单的主 Mermaid 图：

- `取代`：任务 → 任务，记录任务整体改写或被新任务取代的历史。
- `派生自`：候选或任务 → 原始资料/规划依据，记录任务来源，不代表架构层级。
- `参考决策`：正式节点 → `说明/决策/` 下的说明页，只提供追溯入口。

这些辅助关系不能替代 `包含`、`解决`、`涉及系统` 或 `依赖`。

## 架构定位

编译器为每个正式任务计算“当前开发位置”，但不猜测缺失关系：

1. 如果任务通过 `解决` 连接到缺口，再通过 `存在缺口` 连接到系统，则使用该系统的 `包含` 路径定位。
2. 如果任务没有解决缺口，则使用任务的 `涉及系统` 关系定位。
3. 如果任务涉及多个系统，保留多个定位，不强行选择一个主系统。
4. 如果任务既没有缺口链路，也没有 `涉及系统`，生成 warning“任务缺少架构定位”。

总览页以面包屑方式呈现活动任务，例如：

```text
当前开发位置：系统平台 / 数据服务 / 数据导入能力
当前缺口：数据导入缺少幂等校验
当前任务：实现数据导入幂等校验
```

没有明确的 `提供` 关系不能被解释为能力缺失；能力缺失必须来自明确的 `存在缺口` 事实。

## 生成视图

### 总览

`图谱/总览.md` 是入口页，不生成全量关系图。它只呈现：

- 当前 workspace 目标；
- 当前开发位置面包屑；
- 分层视图入口；
- 各系统未解决缺口摘要；
- 进行中、阻塞和下一步任务；
- 待确认候选、冲突和健康 warning。

### 架构地图

`图谱/视图/架构地图.md` 只展示系统的 `包含` 层级、系统提供的能力，以及每个系统的缺口数量摘要。缺口和任务不作为主图节点展开，详情链接到开发路线。

### 开发路线

`图谱/视图/开发路线.md` 按顶层系统分组展示：

```text
系统 → 缺口 → 任务
```

任务显示状态、阻塞原因和下一步；任务依赖使用虚线或独立列表展示，不与架构层级线混用。

### 任务清单

`图谱/视图/任务清单.md` 以表格和小型 Mermaid 图为主，按系统和任务状态分组，集中展示任务、依赖、缺口、代码项目和更新时间。已完成任务默认收纳在折叠列表中。

### 系统联调

`图谱/视图/系统联调.md` 只展示系统之间的 `需要联调` 关系，以及通过 `涉及系统` 定位到这些系统的任务。普通能力和无关任务不进入该视图。

### 索引

`图谱/索引.md` 分开列出四类正式节点、项目支撑记录、决策说明、候选和健康提示，避免把支撑记录伪装成正式图谱节点。

单个视图超过 30 个节点时，按顶层系统拆分章节；系统层级出现循环、多个父级或无法归属时只报告 warning，不自动修正人工事实。

## compile 规则

### 节点识别

- 只从明确的原始资料或用户确认结论创建四类正式节点。
- “可能、考虑、待确认”等内容继续放入候选或待确认项。
- 项目资料识别为支撑记录，不能被编译成正式节点。
- 技术决策识别为说明文档，不能被编译成正式节点。
- 联调事实优先编译为系统间 `需要联调` 关系；详细联调说明才创建普通说明页。

### 重复检查

- 正式节点按“中文类型 + 规范化标题”检查重复。
- 同类型同名或高度疑似同义时生成重复候选，不自动合并、删除或覆盖。
- `能力` 与 `缺口` 即使主题相近，也不能仅凭名称合并；应通过 `目标能力` 关系表达目标与现状问题。
- 支撑记录不参与正式节点统计，也不与正式节点执行同一套类型重复合并。

### 任务状态

- AI 可以提出候选任务，但必须等待用户确认后才创建正式任务。
- AI 不能仅凭子任务完成、依赖变化或代码提交自动改变任务状态。
- 缺口是否已解决也不能仅由任务状态推断，仍需要明确事实或用户确认。

## 迁移策略

迁移只作用于当前 workspace，执行前必须取得用户明确确认，并通过 Obsidian CLI 读写 Vault 内容。

迁移映射如下：

| 旧内容 | 新内容 |
| --- | --- |
| `节点/项目/` | `说明/项目/` |
| `节点/系统/` | `节点/系统/` |
| `节点/能力/` | `节点/能力/` |
| `节点/能力缺口/` | `节点/缺口/` |
| `节点/任务/` | `节点/任务/` |
| `节点/决策/` | `说明/决策/` |
| `节点/联调点/` | `说明/联调/`，保留待处理说明 |

迁移要求：

1. 稳定 ID、来源、正文和历史全部保留。
2. 旧类型、旧路径和旧文件名写入 aliases 或迁移报告。
3. `关联项目` 关系改为项目支撑记录引用或任务的实现项目元数据，不进入主图。
4. 旧联调点不自动伪装成系统、能力或任务；无法转换的内容进入待确认列表。
5. 同类型同名页面保留全部内容，文件名追加稳定 ID 短后缀并生成重复候选。
6. 迁移后重建总览、索引、四个视图并执行链接健康检查。

## 错误处理与健康检查

以下情况是 warning，不阻断可写入的 compile：

- 未解析 Wiki 链接；
- 正式节点孤立或无出链；
- 任务没有架构定位；
- 缺口没有系统或目标能力；
- 系统层级循环、多个父级或无归属；
- 项目/决策说明被错误放入正式节点目录。

Obsidian CLI 不可用、当前 workspace 不可访问、写入失败或迁移过程中出现无法安全保留的冲突时，操作失败且不自动 commit。健康 warning 使用稳定指纹追踪，只在首次出现、状态变化或解决时追加日志。

## 实现范围

实现阶段需要同步以下规范接口：

- `SKILL.md`：使命、目录、类型、关系、compile 和启动上下文；
- `README.md`：用户可见的类型和视图说明；
- `CONTEXT.md`：术语、类型边界和架构定位；
- `templates/SCHEMA.md.example`：Schema、关系端点和布局；
- `action/compile.md`：四类节点识别、定位、视图生成和 warning；
- `action/migrate.md`：旧项目/决策/能力缺口/联调点迁移；
- `references/layered-views.md`：四个视图的边界和规模控制；
- `references/project-state.md`：项目支撑记录和代码现场采集；
- 新增 ADR：记录正式类型精简和支撑记录降级决策。

当前阶段不修改用户知识库中的实际 workspace 内容；实现文档更新后，才由用户明确执行 `migrate` 迁移实际 Vault。

## 验收标准

实现完成后应满足：

1. 所有非历史规范文档只把系统、能力、缺口、任务列为正式图谱类型。
2. 新生成正式节点的目录、文件名和 frontmatter `type` 均使用中文。
3. 项目和决策不会进入架构地图、开发路线和任务清单的主 Mermaid 图。
4. 活动任务能够通过缺口链路或 `涉及系统` 显示架构定位。
5. 架构地图、开发路线、任务清单和系统联调四个视图边界互不混淆。
6. 迁移保留稳定 ID、来源、正文、历史和无法自动转换项。
7. 重复、未定位任务、层级循环和未解析链接只产生可追踪 warning，不静默修复事实。
8. `git diff --check`、Shell 语法检查和文档一致性检查通过；主 skill 与 active install copy 的规范文件一致。
